# Shared Resource Lifecycle

Read this single procedure for initial persistence verification before delegating edits, and before creating/reusing worktrees or disposable build/test copies, large builds (including in the main checkout), dependency/browser installations, archives or other substantial allocations, and cleanup/storage recovery. Reuse already-read instructions and verified setup while applicable. Acceptance and worker lifecycle belong to the execution skills and their shared contract.

In coordinated mode, Coordinator is the run resource owner; Orchestrator is the immediate parent of implementer/validator resources. Orchestrator subdivides its assigned allocation and coordinates increases/shared targets with Coordinator before allocation. Parent duties below apply locally to Orchestrator and globally to Coordinator; reconcile one run ledger without counting a parent reservation and its child allocations twice. Direct Orchestrator performs both duties within its boundary. Resource responsibility survives any worker exit; transfer exact paths, consumers, retained obligations and remaining allocations before the next assignment. A paused/missing parent grants no new cleanup or allocation authority.

## Artifact Placement

Classify artifacts only when the task needs them. Before dispatch or creation, distinguish authored deliverables, working environments and retained evidence using existing project locations; this does not require three new directories. Work in the existing checkout with normal ignored build output needs no new workspace hierarchy or retention table. Reuse established locations and applicable checks; record additional ownership/retention only when there is something to manage. No cleanup-authorization request is needed when no deletion is planned; required persistence, headroom and candidate checks still apply.

| Material | Placement and treatment |
| --- | --- |
| Implementation deliverables, reusable tests/reproduction scripts, contracts and concise chunk records | Normal project locations, visible for intentional Git inclusion; do not bury the only deliverable copy in ignored generated output. |
| Copied repositories, extracted dependencies, virtual environments, generated fixtures, builds, caches and browser profiles | Dedicated workspace/output paths outside authored documentation trees. Inside a repository, verify these paths are ignored and untracked before populating them; external workspaces need explicit ownership and boundaries. |
| Required original observations, candidate evidence and identified deployed/recovery artifacts | Persistent evidence destinations with a stated retention purpose; choose Git inclusion deliberately, not because they happen to live under docs. |

Handwriting a diagnostic helper does not make it a maintained deliverable. Disposable experiments may stay in ignored scratch; promote a helper to normal project locations only when it is intended as reusable project work. Retain it as evidence when required for reproduction. Neither classification makes unique unfinished implementation or required evidence disposable; apply the preservation and release checks below.

Do not ignore an entire specification tree to hide generated environments, force-add workspace contents, or treat an ignore rule as cleanup authority. Reuse compatible working environments during corrections where candidate isolation permits. If unique implementation work or required failure evidence appears in scratch, preserve it persistently before proceeding. Persistence, Git inclusion and retention duration are separate decisions; none implies the others. Apply these rules prospectively without moving or deleting historical artifacts merely to match the layout.

## Persistent Workspaces

Unfinished source must live on persistent storage from the first edit. Verify resolved workspace paths and backing Git/common-directory storage are not temporary, memory-backed or subject to automatic cleanup; a persistent-looking name or `.git` file alone is insufficient. The current checkout may itself be a worktree. Use it for safe sequential work; use isolated worktrees when delegation/concurrency or candidate isolation requires them. Prefer the project's established persistent worktree location. If none is suitable or already authorized, propose one dedicated location and ask once before creation; do not automatically scatter siblings or use `/tmp` as a fallback. Reuse the chosen location and same-chunk workspace; create only needed worktrees.

Record initial workspace/persistence verification once in the existing handoff. A subsequent worker may reuse that evidence after confirming it applies to its actual workspace and operations. Repeat the underlying investigation when paths, storage, ownership or relevant conditions change or become uncertain. This reuse does not replace current candidate verification, write-ownership checks or headroom checks before substantial allocations.

Nested worktrees are allowed only when their paths are ignored and untracked in the containing repository. Verify both before creation; do not force-add them. Ignore rules prevent ordinary staging, not deletion: protect worktree containers and shared Git metadata from broad cleanup, including `git clean -fdx`, and never remove a containing checkout while nested worktrees or dependent Git metadata remain needed. Record workspace/common-directory paths, owners and consumers in the existing durable handoff. Preserve unfinished/held candidates; release integrated worktrees only after the retention and cleanup checks below pass.

Reserve `/tmp` and other disposable storage for reproducible resources. A disposable build/test copy requires a complete persistent source candidate, including staged, unstaged, new/untracked files and required local inputs, with provenance linking the copy to it. No unique implementation edits belong there. Write required evidence and recovery artifacts to persistent destinations as produced, rather than waiting for acceptance or pause. A reboot can happen between handoffs. Persistence does not require premature commits or acceptance. On resume, missing/changed source requires recovery and diff verification before continuation; transcripts/Git metadata are recovery aids, not proof of complete recovery. Reconstructed candidates require applicable revalidation before acceptance.

## Build Operations and Temporary Restrictions

Prefer maintained project commands and established defaults within existing authority. Distinguish ordinary tool-managed regeneration/cache invalidation from discretionary workspace cleanup, and dependency installation from dependency upgrades or tooling installation. Assess relevant actual effects and user/project restrictions; neither calling an operation a build nor calling its output disposable grants permission. Resolve concrete conflicts during existing readiness/preflight work, using established authority rather than a new universal questionnaire. Explicit installation, deletion, retention and shared-cache restrictions still apply.

Before disabling ordinary build behavior to preserve artifacts, check whether required evidence/recovery inputs are already preserved and whether an active consumer still needs the originals. Preservation may remove that justification; it does not itself authorize deletion. A temporary run restriction does not justify a permanent project default. Apply [Supporting Changes and Requirement Authority](../../coordinator/references/execution-contract.md#supporting-changes-and-requirement-authority) before proposing tooling changes; prefer an existing authorized way to satisfy the requirement, without an ad hoc bypass. If none exists, hold the affected operation and identify the exact authority conflict while continuing only independently authorized work.

## Temporary Resources and Cleanup

Where project/user instructions permit, authorization to run orchestration includes routine cleanup of its recorded, disposable resources after the checks below pass. At launch, record the named workspace roots, deletion scope and authority source, and carry them into assignments. If project instructions require explicit authorization for destructive commands, obtain or reuse one explicit bounded cleanup authorization before relying on automatic deletion; ordinary implementation permission does not override that requirement. Do not ask repeatedly within granted bounds. Explicit retention/no-deletion instructions and pauses remain binding. Without authority, retain resources and report cleanup pending; continue independent safe work where permitted. Reading a skill or standalone planning/implementation/validation does not authorize orchestration cleanup. Earlier resources in the same resumed run qualify only after ownership and release checks; unknown ownership or files predating the run do not qualify.

Maintain a compact record in the existing handoff of exact run-created workspace/artifact paths, purpose/owner, named active or future consumers, and release condition. Group resources with the same lifecycle; do not inventory every generated file or run recurring repository censuses. Register resources when created and transfer specific obligations when a worker exits; a closed agent does not make its files disposable. On resume, reconcile relevant records against actual resources before reuse/removal. Do not infer ownership from a filename prefix, age or location under `/tmp`.

Use these disk defaults automatically unless explicit project/run instructions override them; record any override in the existing handoff. Per filesystem, below **5 GiB free** means report low headroom and serialize large allocations; **2 GiB or less free** means a critical disk-space blocker and pause write-heavy work. They are operating defaults, not proof that a particular build fits.

Before large builds, dependency/browser installations, checkout copies or archives, the parent checks every receiving filesystem and coordinates active/planned allocations there. Admit a start only when measured free space minus their conservative remaining additional peak, including the proposed operation, stays above the critical reserve. Account for starts already authorized to other workers before authorizing another; different directories may share one filesystem. If combined peak is uncertain, serialize and reassess; if even the single operation's headroom cannot be established, hold it. Use existing handoff/assignment notes, not a quota service. Workers must coordinate additional large allocations outside their assigned scope with the parent. Prefer compatible existing environments without sharing mutable candidate inputs or violating isolation.

Recheck before large allocations and after substantial allocations or cleanup, rather than after every command. Completion releases an allocation assignment, not its retained bytes: remeasure free space and account for remaining consumers before scheduling more work. No continuous monitoring system is required.

At observed critical space, or any disk-full/quota/inode-exhaustion error regardless of free bytes, stop launching affected writes, safely halt affected owned write-heavy operations and immediately report the blocker. State the filesystem, available capacity/error, held operations, known run-owned resources and eligible cleanup or needed user intervention. Do not retry failed writes, launch a large emergency archive or treat partial outputs as valid evidence. Only already-authorized bounded cleanup may reclaim resources; do not invent deletion authority or override a user pause. Independent read-only work may continue only if safe and authorized; stop the run when storage pressure prevents reliable work globally. Resume affected writes only after rechecking safe headroom and allocation conditions; inspect potentially partial/corrupt outputs, restore candidate identity and rerun affected checks before acceptance.

At validation release, acceptance, abandonment or pause/handoff, the immediate parent resolves resources as still in use, retained for a specific obligation, or disposable after preservation/release checks. Preserve required original observations, unique failed/unfinished state, uncommitted source, necessary reproduction inputs and identified deployed/recovery artifacts. Retain a bulky workspace only with a named consumer or concrete release condition. Prefer source identity, reproduction scripts/configuration and necessary unavailable inputs over complete environment copies where sufficient; hashes or a lockfile alone do not reproduce unavailable inputs. A failed run does not require every dependency extraction, generated fixture or historical build forever. Candidate immutability during validation is mandatory but does not imply permanent workspace retention afterward.

Before releasing an evidence-bearing workspace, preserve the required artifacts in the agreed durable location, verify they remain readable/identifiable, and update references. Keep original failure identity; do not leave the only evidence behind a deleted temporary path. Moving bytes to the same filesystem is not space reclamation, and copying entire disposable workspaces or committing bulky generated output is not the default preservation method.

Use the run's bounded cleanup scope, carried into each assignment. Check each exact path is run-owned and within that scope, with no active process/validator, retained artifact or pending consumer depending on it. Release owned processes/handles before removal, respecting pauses and operational authority. Do not traverse symlinks/mounts into unrelated locations, clear `/tmp` broadly, delete by wildcard/prefix, or prune shared caches, files predating the run, user files or resources belonging to other runs. Worker resources may be cleaned by the parent after a recorded ownership handoff, subject to the same authorization and release checks; resources still owned by another worker remain protected. Use the owning tool's safe lifecycle for managed resources such as Git worktrees, without forced removal of uncommitted work. If ownership, retention or authority is unclear, keep the resource and ask with concrete paths/reasons.

Perform eligible cleanup at lifecycle boundaries rather than waiting for disk pressure. Orchestrator resolves chunk resources; Coordinator revisits resources held for a downstream gate when that gate completes or is abandoned. Direct Orchestrator owns both duties within its scope. Transfer concrete retention/authority obligations, not an undifferentiated "preserve all" instruction. Do not generate blanket permanent-retention or no-cleanup rules by default; honor existing explicit restrictions and seek reconciliation when they prevent release.

After accepted integration and at run closure, verify preservation, rollback needs and consumer release for redundant copies, then remove eligible resources or record an owner, specific retention condition or pending cleanup authorization. Acceptance is not deletion permission, and an evidence archive alone does not establish disposability. Distinguish implementation acceptance from resource closure; do not imply cleanup is complete while it remains pending. Record removed and retained paths in the existing handoff and remeasure headroom after substantial cleanup. Preserve inventory when a pause prevents cleanup, never relax acceptance to recover space, and obtain separate authority for cleanup beyond run-owned scope.
